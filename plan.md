# GitHub App Token Service - Implementation Plan

## Purpose

Generate scoped GitHub App installation tokens for devpods without exposing the GitHub App private key. Devpods can only obtain tokens for repositories they were explicitly registered for. Registration requires user approval via Touch ID.

## Definitions

- **Token Service**: Central service holding GitHub App credentials, running on dev server
- **Devpod**: Containerized development environment that needs GitHub API access
- **User**: Human developer who owns the SSH key and approves registrations
- **Devpod Keypair**: Asymmetric keypair generated by each devpod for authenticating token requests
- **User SSH Key**: User's personal SSH key, protected by Touch ID, used only for registration approval
- **Installation Token**: GitHub App token scoped to specific repositories, expires after 1 hour

## Components

### Token Service

Location: Central docker container on dev server

Stores:
- GitHub App ID
- GitHub App private key
- User's SSH public key (for verifying registrations)
- Registry of devpod registrations (devpod_public_key → allowed_repos)

Endpoints:
- `POST /register` — Register a new devpod (requires user SSH signature)
- `POST /token` — Get an installation token (requires devpod signature)
- `DELETE /register/{devpod_id}` — Remove a registration (requires user SSH signature)

### Devpod Client

Location: Inside each devpod container

Stores:
- Devpod private key (generated on first run)
- Devpod public key

Has access to:
- Forwarded SSH agent (user's key, requires Touch ID for each signature)

## Registration Flow

Preconditions:
- User's SSH agent is forwarded to devpod with confirmation enabled
- Token service has user's SSH public key configured
- Devpod has generated its own keypair

Steps:
1. Devpod creates registration request containing: devpod_public_key, requested_repos
2. Devpod signs registration request using user's SSH key via forwarded agent
3. SSH agent prompts user for Touch ID on their local machine
4. User approves via Touch ID
5. Devpod sends registration request + signature to Token Service `POST /register`
6. Token Service verifies signature against configured user SSH public key
7. Token Service stores mapping: devpod_public_key → allowed_repos
8. Token Service returns success

Result: Devpod is now registered and can request tokens autonomously.

## Token Request Flow

Preconditions:
- Devpod is registered
- Devpod has its private key

Steps:
1. Devpod creates token request
2. Devpod signs token request using its own devpod private key
3. Devpod sends request + signature to Token Service `POST /token`
4. Token Service verifies signature against registered devpod_public_key
5. Token Service retrieves allowed_repos for this devpod
6. Token Service generates GitHub installation token scoped to allowed_repos only
7. Token Service returns installation token to devpod

Result: Devpod has a 1-hour token scoped to its registered repositories.

Note: This flow does not require user interaction.

## Token Usage Flow

Steps:
1. Devpod uses token for GitHub operations (API calls, git clone, gh CLI)
2. When done, devpod revokes token by calling GitHub API: `DELETE /installation/token`

## SSH Signing Mechanism

Purpose: Prove that a human user authorized the registration.

How it works:
- `ssh-keygen -Y sign` can sign arbitrary data
- When given a public key path, it requests the signature from the SSH agent
- The SSH agent forwards the request to the user's local machine
- If the key was added with confirmation (`ssh-add -c`), Touch ID is triggered
- The signature is returned without the private key ever leaving the user's machine

Verification:
- Token Service uses `ssh-keygen -Y verify` with an allowed_signers file
- Allowed signers file contains the user's SSH public key

## Security Properties

1. GitHub App private key never leaves Token Service
2. Devpod compromise only exposes pre-registered repositories
3. Devpod cannot register itself for additional repos without user Touch ID approval
4. User SSH private key never leaves user's local machine
5. Token requests are autonomous (no user interaction after registration)
6. Tokens are short-lived (1 hour) and should be revoked after use

## Data Structures

### Registration Entry

```typescript
interface RegistrationEntry {
  devpod_id: string;              // unique identifier
  devpod_public_key: string;      // SSH public key format
  allowed_repos: string[];        // e.g., ["org/repo-a", "org/repo-b"]
  user: string;                   // who authorized this registration
  created_at: Date;
}
```

### Token Request

```typescript
interface TokenRequest {
  devpod_id: string;
  timestamp: Date;                // for replay protection
  signature: string;              // signed by devpod private key
}
```

### Token Response

```typescript
interface TokenResponse {
  token: string;                  // GitHub installation token
  expires_at: Date;               // 1 hour from creation
  repositories: string[];         // repos this token can access
}
```
